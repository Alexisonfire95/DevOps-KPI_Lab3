## Середовище експериментів
* **Хост-ОС:** Windows (з використанням Docker Desktop, двигун WSL2)
* **Версія Docker:** 29.x або новіша (active context: `desktop-linux`)
* **Конфігурація CPU/RAM:** Використовуються апаратні ресурси хоста.

## 1. Python Application

Репозиторій для експериментів: `experiments/lab2/python-starter`.

### Опис докерфайлів
* **Dockerfile.naive:** Проста збірка, де спочатку копіюється весь проєкт (`COPY . .`), а вже потім встановлюються залежності через `pip`.
* **Dockerfile.optimized:** Оптимізована збірка з кешуванням шарів: спочатку копіюється тільки `requirements/backend.in` та запускається `pip install`, а потім копіюється решта коду.
* **Dockerfile.optimized.alpine:** Аналогічно optimized, але базовий образ змінено з Debian (`python:3.13-bookworm`) на Alpine (`python:3.13-alpine`).

### Отримані метрики

| Експеримент | Час збірки | Розмір образу |
|---|---|---|
| **naive v1** (Debian, чистий кеш) | ~60s | 1.54GB (Content: 398MB) |
| **naive v2** (Debian, після зміни коду) | ~12s | 1.54GB (Content: 398MB) |
| **optimized v1** (Debian, чистий кеш) | ~55s | 1.54GB (Content: 398MB) |
| **optimized v2** (Debian, після зміни коду) | **0.2s (CACHED)** | 1.54GB (Content: 398MB) |
| **optimized alpine v1** (Alpine, чистий кеш) | ~15s | 133MB (Content: 32.5MB) |
| **optimized debian + numpy** | ~12s (wheel) | 1.63GB (Content: 418MB) |
| **optimized alpine + numpy** | ~15s (wheel) | 232MB (Content: 54.7MB) |

*Примітка: У нових версіях Docker Desktop розмір на диску відображається у вигляді DISK USAGE (віртуальний диск WSL2) та CONTENT SIZE (реальний розмір розпакованих шарів).*

### Висновки (Python)
1. **Кешування шарів (Layer Caching):** У `naive` варіанті будь-яка зміна коду (навіть один символ в `index.html`) призводить до скидання кешу на шарі `COPY . /app`. Як наслідок, наступний крок `RUN pip install` виконується наново, що марнує час та мережевий трафік. В `optimized` варіанті копіювання залежностей винесено вище коду, тому зміна коду не впливає на кеш встановлення бібліотек (збірка проходить миттєво — за 0.2 сек).
2. **Alpine Linux:** Використання Alpine як базового образу кардинально зменшує фінальний розмір (з ~1.5 ГБ до 133 МБ). Це критично важливо для швидкості передачі образів через мережу (push/pull).
3. **Залежності на Alpine:** Встановлення важких C-пакетів (як-от `numpy`) на Alpine раніше вимагало тривалої компіляції, але зараз завдяки `musllinux` wheels на PyPI збірка проходить швидко, а розмір образу лишається мінімальним (54.7MB проти 418MB на Debian).

## 2. Musl (Alpine) vs glibc (Debian/Ubuntu)

Експеримент проведено в Docker-мережі `dns-lab` з використанням локального DNS-сервера `dnsmasq` (IP: `172.18.0.2`, домен `myservice.internal.corp`).

### Результати перевірки
* **Контейнер Ubuntu (glibc):** Команда `getent hosts myservice.internal` успішно повернула IP-адресу:
  ```
  10.0.0.50       myservice.internal.corp
  ```
* **Контейнер Alpine (musl):** Команда `nslookup myservice.internal` повернула помилку:
  ```
  ** server can't find myservice.internal: NXDOMAIN
  ```

### Причина та аналіз логів DNS
Згідно з логами DNS-сервера:
* Контейнер **Ubuntu** надіслав запит на ім'я `myservice.internal.corp` (автоматично додавши суфікс із `search corp`). Це пов'язано з тим, що `glibc` реалізує послідовний пошук: якщо ім'я містить крапки, але не закінчується крапкою, і кількість крапок менша за `ndots` (за замовчуванням 1), він спочатку намагається додати суфікси з пошукових доменів.
* Контейнер **Alpine** надіслав запит тільки на ім'я `myservice.internal` і, отримавши відповідь `NXDOMAIN`, завершив роботу. `musl libc` не підтримує таке саме розширення імен з крапками через `search` суфікси. Він вважає будь-яке ім'я з крапкою повноцінним доменом (FQDN) і не намагається підставляти суфікси.

### Наслідки в реальних системах
Така поведінка може призвести до прихованих помилок при перенесенні сервісів на Alpine у mixed-середовищах (наприклад, у Kubernetes), коли контейнери не можуть достукатися до сусідніх мікросервісів за короткими локальними іменами (як-от `database.local`).

## 3. Golang + Multi-stage Builds

Репозиторій для експериментів: `experiments/lab2/golang-starter`.

### Опис докерфайлів
* **Dockerfile.single:** Одностадійна збірка на базі образу `golang:1.24-bookworm`.
* **Dockerfile.multistage.scratch:** Багатостадійна збірка, де компіляція відбувається в образі Go, а скомпільований бінарний файл копіюється у повністю порожній образ `scratch`.
* **Dockerfile.multistage.distroless:** Аналогічно, але бінарник копіюється в мінімальний образ `gcr.io/distroless/static-debian12:nonroot`.

### Метрики

| Кейс | Час збірки | Розмір образу |
|---|---|---|
| **single-stage** | ~18s | 1.41GB (Content: 339MB) |
| **multi-stage scratch** | ~11s | 19.4MB (Content: 6.88MB) |
| **multi-stage distroless** | ~12s | 25.6MB (Content: 7.59MB) |

### Висновки (Golang / Multi-stage)
1. **Image Bloat:** Одностадійна збірка тягне за собою весь Go SDK, компілятор, інструменти збірки та вихідний код. Це створює величезний образ (1.41 ГБ), який не потрібен для звичайного запуску програми.
2. **Багатостадійність (Multi-stage):** Дозволяє відокремити середовище збірки від середовища запуску. Ми копіюємо в фінальний образ тільки бінарний файл (~7 МБ) та папки шаблонів.
3. **Scratch vs Distroless:** 
   * Образ `scratch` є максимально мінімальним (19.4MB), але він порожній. У ньому немає шела (`/bin/sh`), утиліт діагностики (curl, ping) та сертифікатів SSL (якщо додатку треба робити HTTPS запити). Це ускладнює дебаг.
   * Образ `distroless` (25.6MB) є чудовим компромісом. Він важить майже так само мало, але містить мінімально необхідні системні бібліотеки, ca-certificates, таймзони та системних користувачів, при цьому залишаючись безпечним (без шела та зайвого ПЗ).
